LAB OVERVIEW

What this lab is about

This lab recreates, on virtual machines, the way a real organisation runs its internal certificate authority. The Root CA is built first and then taken offline, because it is the single most valuable key in the whole hierarchy. It never signs anything day to day — its only job is to sign the Subordinate CA once. The Subordinate CA is the online issuing authority: it is joined to an Active Directory domain, publishes its certificate revocation list (CRL) over HTTP through IIS, and issues certificates to domain users automatically through Group Policy auto-enrollment.

I then tested the full lifecycle — issuing a certificate, revoking it, publishing a fresh CRL, and confirming from a client machine that the revocation is detected. Every error I hit along the way is recorded in the Issues & Resolutions section.

ROOT-CA

Standalone, offline, air-gapped Root CA. Not domain-joined and not on any network.

DC01

Domain Controller for lab.local with AD DS, DNS and Group Policy.

SUB-CA

Enterprise Subordinate CA, domain-joined, with IIS publishing CDP/AIA over HTTP.

CLIENT01

Domain-joined client that auto-enrolls for certificates and verifies revocation.

Lab Architecture

PKI HIERARCHY · TRUST PATH · CERTIFICATE LIFECYCLE  (swipe sideways on mobile)
  • 1Signing ceremony — the Sub CA request is carried to the offline Root over the VMware shared folder, signed, and carried back. This is the only link between the two.
  • 2Domain services — DC01 provides DNS, authentication, and Group Policy to SUB-CA and CLIENT01, and holds the CA certificates published to AD.
  • 3Enrollment — CLIENT01 receives the auto-enrollment policy and obtains a certificate from the SUB-CA using the LabUserCert template.
  • 4Revocation check — clients fetch the CRL over HTTP from the SUB-CA's IIS site to confirm whether a certificate is still valid.

WHY

Why I built this lab

Reading about PKI explains the vocabulary, but building one forces every design decision to be made and every failure to be diagnosed. I wanted to build a certificate hierarchy from nothing — choose the key sizes, decide what stays offline, plan where revocation information is published, integrate the CA with Active Directory, and then prove it works by revoking a certificate and watching a client detect it.

Nothing in this lab was copied from a template, and nothing was hidden when it broke — the errors and fixes are documented below.

WORK DONE

What I built, stage by stage

1

Built the offline Root CA

MACHINE · ROOT-CA
WHAT I DID
  • Set up a standalone Windows Server VM (ROOT-CA) that is not joined to any domain and has no network connection to the lab.
  • Installed Active Directory Certificate Services and configured it as a Standalone Root CA with a 4096-bit key, SHA256 hashing and 15-year validity.
  • Changed the CRL period to years so the CRL stays valid while the Root is powered off, then published the first CRL.
Install-AdcsCertificationAuthority -CAType StandaloneRootCA `
  -KeyLength 4096 -HashAlgorithmName SHA256 `
  -ValidityPeriod Years -ValidityPeriodUnits 15
certutil -setreg CA\CRLPeriod "Years"
certutil -crl
WHY
4096 bits for a 15-year trust anchor. A long CRL period suits a CA that is powered off for most of its life.
2

Built the domain controller

MACHINE · DC01
WHAT I DID
  • Set the local Administrator password, then promoted the server to a Domain Controller by creating a new forest, lab.local.
  • Gave DC01 a static IP and used it as the DNS server for the lab, so every other machine can find the domain.
Install-ADDSForest -DomainName "lab.local"
WHY
An Enterprise CA needs Active Directory — templates, auto-enrollment and certificate publication all depend on it.
3

Prepared the Subordinate CA and generated its request

MACHINE · SUB-CA
WHAT I DID
  • Pointed the SUB-CA's DNS at DC01 and joined it to lab.local.
  • Installed AD CS and started the Enterprise Subordinate CA setup with a 2048-bit key and SHA256.
  • The setup produced a certificate request (.req file) instead of a working CA — the Sub CA cannot issue anything until the Root signs it.
Install-AdcsCertificationAuthority -CAType EnterpriseSubordinateCA `
  -KeyLength 2048 -HashAlgorithmName SHA256
WHY
This is what makes the hierarchy two-tier: the issuing CA gets its authority from the Root, not from itself.
4

Performed the signing ceremony across the air gap

MACHINES · SUB-CA → ROOT-CA → SUB-CA
WHAT I DID
  • Copied the .req file from SUB-CA to a VMware shared folder (PKI-Transfer), the only transfer path between the machines.
  • Powered on ROOT-CA, submitted the request, issued it from the Root CA console, and exported the signed SubCA.crt.
  • Copied the signed certificate and the Root certificate back through the shared folder, then powered the Root CA off again.
certreq -submit SUB-CA.lab.local_LabSubCA.req
certreq -retrieve <RequestID> SubCA.crt
WHY
No network path to ROOT-CA exists by design. Moving files by hand, every time, is the offline-root discipline real CAs follow.
5

Installed the signed certificate and established trust in the Root

MACHINE · SUB-CA
WHAT I DID
  • Installed the signed certificate on SUB-CA to complete its setup.
  • Published the Root CA certificate into Active Directory so every domain machine trusts it automatically.
  • Set a CA registry flag so the service can start while its issuer (the Root) is offline, then started Certificate Services.
certutil -installcert SubCA.crt
certutil -setreg ca\CRLFlags +CRLF_REVCHECK_IGNORE_OFFLINE
certutil -dspublish -f RootCA.crt RootCA
WHY
Certificate Services checks its issuer's revocation status at startup. With a deliberately offline Root, that check has to be told to stand down.
6

Set up CRL and AIA publication over HTTP using IIS

MACHINE · SUB-CA
WHAT I DID
  • Installed the IIS web server role on SUB-CA to host the CRL and CA certificate files.
  • Configured the CA to publish revocation information (CDP) and issuer information (AIA) at an HTTP location, and published a fresh CRL.
  • Verified that the files are reachable by URL, so any client can check revocation — not only AD-aware ones.
Install-WindowsFeature Web-Server
certutil -crl
WHY
HTTP publication lets any client, domain-joined or not, check whether a certificate has been revoked.
The Root CA's own certificate carries no CDP/AIA at all — this is correct, not missing. A trust anchor is trusted directly from the machine store.
7

Created a certificate template and enabled auto-enrollment

MACHINES · SUB-CA, DC01, CLIENT01
WHAT I DID
  • Duplicated the built-in User template as LabUserCert and published it on the SUB-CA.
  • Created a Group Policy that turns on certificate auto-enrollment under Public Key Policies.
  • Joined CLIENT01 to the domain, applied the policy, and confirmed that the domain user received a certificate automatically with no manual request.
  • Added an email address to the user's AD account because the template required one, then confirmed it appears in the certificate's Subject Alternative Name.
certtmpl.msc  → duplicate "User" → LabUserCert
GPO: Public Key Policies → Auto-Enrollment → Enabled
WHY
In Enterprise PKI a domain user should never have to request a certificate by hand.
8

Tested the full certificate lifecycle

MACHINES · SUB-CA, CLIENT01
WHAT I DID
  • Verified the complete chain Root → Sub CA → issued certificate from the client.
  • Revoked the issued certificate on the SUB-CA and published a new CRL.
  • Ran a verification from CLIENT01 that downloads the CRL over HTTP, and confirmed the client correctly reported the certificate as revoked.
certutil -verify -urlfetch Samplecert.cer
→ The certificate is revoked. 0x80092010 (CRYPT_E_REVOKED)
WHY
Issuing a certificate proves little by itself. Revoking it and watching a client detect that over HTTP proves the whole chain works end to end.

DESIGN NOTE // ROOT CA HAS NO CDP

A root's self-signed certificate is trusted directly from the local trust store — nothing above it needs to check its revocation status. Real-world roots commonly ship without a CDP/AIA on their own certificate for this reason. Adding one here would contradict the minimal, offline-by-design footprint this lab exists to demonstrate.

ISSUES & RESOLUTIONS

Problems I hit and how I fixed them

BLOCKED#01 · AD DS promotion

Blank local Administrator password

Prerequisites failed: local Administrator password does not meet requirements
CAUSEThe server's local Administrator account had a blank password, which AD DS promotion does not accept.
FIXSet the password from the command line with net user Administrator <password>. This was more reliable than the GUI dialog, which can silently miss the VM if Ctrl+Alt+Delete is captured by the host.
BLOCKED#02 · Domain join

DNS pointed at the wrong server

0x0000232B RCODE_NAME_ERROR — AD DC could not be contacted
CAUSESUB-CA was using VMware's NAT DNS instead of DC01, so it could not resolve lab.local. Confirmed with nslookup lab.local.
FIXPointed the SUB-CA's DNS setting at DC01's static IP. The domain join then succeeded.
INFO#03 · File transfer

CMD rejects UNC paths as a working directory

CMD does not support UNC paths as current directories
CAUSENot a configuration fault — Command Prompt cannot use a network path as its current directory.
FIXMapped the share to a drive letter with net use Z: \\vmware-host\Shared Folders\PKI-Transfer and worked from Z: instead of using cd on the UNC path.
FALSE ALARM#04 · Certificate install

Looked broken, was already done

0x8007139f ERROR_INVALID_STATE
CAUSEThe error appeared because the signed certificate had already been installed on an earlier attempt.
FIXcertutil -verify showed the chain was already valid, so nothing needed repair. The real blocker was the service startup error (#05).
BLOCKED#05 · Certificate Services startup

Service refused to start against an offline issuer

Service error 2148081683 — CRYPT_E_REVOCATION_OFFLINE
CAUSEOn startup the CA checks the revocation status of its issuer. The Root CA is offline by design, so the check could not complete.
FIXRan certutil -setreg ca\CRLFlags +CRLF_REVCHECK_IGNORE_OFFLINE — Microsoft's documented setting for exactly this offline-root layout — and restarted the service.
INFO#06 · Revocation check

HTTP CDP silently falling back to LDAP

ERROR_WINHTTP_NAME_NOT_RESOLVED on the HTTP CDP path
CAUSESame root cause as #02 — the client's DNS was not resolving the SUB-CA's hostname, so the HTTP URL failed and Windows fell back to LDAP.
FIXAdded a temporary HOSTS entry on the test machine to prove the HTTP path works. The proper fix is DNS pointed at DC01 on every machine.
